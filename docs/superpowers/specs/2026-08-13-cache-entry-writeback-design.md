# JapanPost-SaaS 快取、唯一入口與回填可靠性設計

## 目標

在不大幅改動現有新版郵局頁面 UI 的前提下，完成三項短期修復：

1. 使用者登入主頁後，自動取得跨境揀貨單與郵局待製資料，並在活躍期間以 20 分鐘為資料新鮮度界線。
2. 將「郵局待打單（新版測試）」提升為唯一郵局製單入口並更名為「待製郵便運單」，移除舊版入口。
3. 修復製單完成後寫回 Google Sheets 的可靠性缺口，特別是工作表列數不足、下一列判斷、追加製單、防重與讀回驗證。

本設計只處理現有 Streamlit 站的短期修復。常駐服務與商業個資合規託管另案規劃。

## 已確認現況

- 跨境揀貨單與郵局待製資料目前都要按「重新讀取」才會從 Google Sheets 載入。
- 待製資料只存於各使用者的 `st.session_state`，不是跨 session 共享快取。
- 舊版與新版郵局頁面共用同一套 `_start_job()`、郵局自動化、雙重防重與 `backfill_results()` 管線；新版沒有漏接回填功能。
- 回填目前只依 B 欄最後非空列決定寫入位置，直接寫 B:D 與 J，未先確認或擴充 worksheet grid。
- 寫入後目前只驗證 C、D，沒有完整驗證 B、C、D、J。
- 現有 fake worksheet 沒有 `row_count` 限制，因此無法發現正式工作表列數不足。
- Streamlit Community Cloud 在無流量時會休眠；App 內計時不能在休眠期間執行。本設計不把 20 分鐘刷新描述為常駐排程或喚醒機制。

## 方案選擇

採用 process 內共享快照、進站新鮮度檢查與活躍 session 定時檢查。

未採用的替代方案：

- 僅使用 session 快取：每位使用者仍會各自讀取 Google Sheets，無法提升後續使用者的進站速度。
- 背景 thread 常駐刷新：容器休眠、重啟或重新部署後不可靠，且增加併發與生命週期風險。
- 外部 ping 當核心喚醒：無法保證通過 Streamlit 休眠頁、OAuth 與 WebSocket，也不能證明 Python 資料快取已更新。

## 共享快取架構

新增一個責任單一的共享刷新協調器，分別管理：

- 跨境揀貨單快照。
- 郵局待製資料快照。

每份快照只保存：

- 最近一次成功取得的資料。
- 最後成功時間。
- 最後一次刷新錯誤的安全化分類。
- 保護刷新流程的單飛鎖。

協調器行為：

1. 使用者通過登入並進入主頁時，頁面要求兩份資料。
2. 快照存在且未滿 20 分鐘時，回傳資料副本，不呼叫 Google Sheets。
3. 快照不存在或已過期時，只允許一個執行者刷新相同資料源。
4. 同時進站的其他使用者不得重複觸發相同讀取；有舊快照時可繼續取得舊資料，沒有快照時等待同一刷新結果。
5. 手動「重新讀取」使用相同協調器，但明確要求強制刷新。
6. 刷新失敗時保留上一份成功快照，不以空資料覆蓋。
7. 每次交給 session 或編輯器的 DataFrame 都是副本；使用者編輯不得污染共享快照。
8. Streamlit process 重啟後共享快照自然清空，下一次進站重新載入，不將記憶體快取當成永久資料層。

Streamlit 1.56 的活躍 session 定時片段每 20 分鐘檢查一次資料新鮮度。它只在頁面保持活躍時執行。製單或編輯狀態尚未安全結束時，不用新快照覆蓋使用者畫面；工作完成或離開編輯狀態後才套用最新資料。

## 主頁載入與失敗行為

- 登入主頁後自動載入兩份資料，不再要求使用者先進入各頁按「重新讀取」。
- 其中一份載入失敗不得阻止另一份資料顯示。
- 有舊資料時，以舊資料繼續工作並顯示簡短的人類可讀提示。
- 完全沒有可用資料時，該頁顯示明確失敗提示與重新嘗試按鈕。
- Google API 錯誤、鎖狀態、快取秒數及內部例外只記錄於安全化日誌，不堆疊在主要操作畫面。

## 郵局唯一入口

主頁頁籤調整為：

1. 跨境揀貨單
2. 待製郵便運單
3. 使用說明
4. 讀取診斷

入口重整規則：

- 「待製郵便運單」沿用目前新版測試頁面的卡片排版、全選／清除、編輯欄位與操作順序。
- 移除「郵局待打單」舊頁籤及只供舊頁面使用的渲染狀態。
- 清除使用者可見的「新版」「測試版」「舊版」字樣。
- 共用驗證、即時雙重防重、背景工作、郵局自動化及回填函式維持單一後端，不複製管線。
- 刪除舊渲染程式前，先證明被刪函式不是新版或共用後端的相依項。

## UI／UX 原則

原本新版排版已符合使用需求，本次不進行視覺重做。

- 正常情況只在「重新讀取」附近低調顯示最後資料更新時間。
- 自動刷新期間只使用簡短載入提示，不改變主要版面層級。
- 有舊資料可用時，提示「暫時無法取得最新資料，目前顯示上次成功讀取的內容」。
- 不在主要頁面顯示快取筆數、過期秒數、鎖狀態、API 錯誤代碼或內部欄位。
- 「讀取診斷」只保留人工排錯所需資訊，詳細資料仍留在安全化日誌。
- 自動更新暫停套用屬內部保護，不新增干擾操作的 UI。
- UI 驗收包含排版與實際操作體驗沒有非必要退步，不以功能測試通過取代視覺驗收。

## 回填資料契約

固定目標仍為既有 Google Spreadsheet 與 GID。既有欄位契約維持：

- B：收件人。
- C：注文番号。
- D：追跡番号。
- J：國家代碼。

需求文件另提到日期，但目前沒有已驗證的目標欄位。本次不得猜測欄位後寫入。若能以不讀取業務資料的方式確認標題列與日期欄位，再另行納入明確契約。

## 下一列與工作表容量

回填前重新取得 B、C、D、J 的必要資料，依所有相關欄位判斷最後使用列，不再只依 B 欄。

1. 計算本批每個實際運單結果所需的目標列。
2. 比對 worksheet `row_count`。
3. 若最後目標列超過 grid，先使用 worksheet 的擴列能力補足容量。
4. 擴列成功後才執行 B:D 與 J 的批次寫入。
5. 擴列或寫入失敗時，不把工作狀態標記為完成。

公式空字串、B 空但 C／D 已有值及零散殘值都必須納入下一列判斷測試，避免覆蓋既有紀錄。

## 追加製單與防重規則

唯一性以「注文番号＋追跡番号」組合判斷，但不同追跡番号不是概括合法。

- 一般製單未設定追加製單：每個注文番号只應產生一筆追跡番号與一列回填資料。
- 使用者明確提交追加製單：同一注文番号可產生原始運單與追加運單；本次製單結果明確返回的每個追跡番号各新增一列。
- 系統只回填本次製單結果明確返回的運單，不能因工作表已有相同注文番号就自行推定需要另一張運單。
- 注文番号與追跡番号完全相同：視為相同包裹的重試成功，不重複新增。
- 同一注文番号出現不同追跡番号，且各筆都是本次追加製單的明確結果：分別新增。
- 未提交追加製單且缺少同等明確證據，卻出現同一注文番号的不同追跡番号：不自動寫入該異常結果，標記待人工確認。
- 同一追跡番号對應不同注文番号：視為資料衝突，不自動覆寫。
- 已有注文番号但追跡番号空白時，只有能唯一證明是本次運單留下的未完成列才補齊；否則不猜測或覆寫。

每個包裹獨立記錄回填結果，單筆失敗不得把其他已驗證成功的包裹誤標為失敗，也不得因其他筆成功而把失敗筆標為完成。

## 寫入後驗證與錯誤狀態

1. 執行 B:D 與 J 的批次寫入。
2. 重新讀取本批目標列的 B、C、D、J。
3. Google Sheets 可能有短暫讀回延遲，因此允許有限次、帶間隔的讀回重試。
4. 四欄全部與預期一致，該包裹才標記為回填成功。
5. 讀回仍不一致時，依實際結果標記為回填失敗、部分回填、資料衝突或等待人工確認。
6. 整個製單工作只有在必要包裹都取得可接受的終態後，才顯示完成。

日誌可記錄工作表容量、目標列、成功／失敗筆數、錯誤類型與 correlation id；不得輸出收件人、完整注文番号、追跡番号或其他個資。

## 程式邊界

- 新增獨立共享刷新協調器，避免讓 `app.py` 繼續承擔鎖與 TTL 細節。
- 現有跨境揀貨與郵局載入器維持各自的資料讀取、整理與篩選責任。
- `bot/sheets.py` 維持 Google Sheets target、擴列、寫入與讀回驗證責任。
- Streamlit 頁面只負責要求資料、保留使用者編輯狀態、觸發刷新與顯示簡潔狀態。
- 不建立第二套製單或回填後端。

## 測試設計

### 共享快取

- 首次要求會載入資料。
- 20 分鐘內重用共享快照。
- 到期後重新載入。
- 多個並行呼叫只執行一次 loader。
- 強制刷新忽略 TTL。
- 刷新失敗時沿用上一份成功快照。
- 沒有舊快照且刷新失敗時回傳明確失敗。
- 回傳 DataFrame 副本，呼叫端修改不污染共享資料。
- 兩個資料來源其中一個失敗不阻止另一個成功。

### 回填

- 目標列超過 `row_count` 時先擴列再寫入。
- B 空但 C／D 有值時不覆蓋。
- B 欄公式空字串與零散值不造成錯誤寫入位置。
- 一般製單只接受本次單一運單結果。
- 明確追加製單的多個追跡番号分別新增。
- 完全相同的注文番号＋追跡番号重試不重複新增。
- 無追加證據的異常第二追跡番号轉為待人工確認。
- 相同追跡番号對應不同注文番号時停止自動寫入。
- grid-limit、權限與暫時網路錯誤不會被標為成功。
- 部分寫入與讀回延遲會得到正確狀態。
- B、C、D、J 四欄都接受讀回驗證。

### UI 與整合回歸

- 登入主頁會自動要求兩份資料。
- 手動重新讀取會強制刷新正確資料源。
- 製單／編輯期間不套用新快照覆蓋使用者狀態。
- 頁籤只保留「待製郵便運單」，舊名稱完全消失。
- 新版頁面仍呼叫既有 `_start_job()` 與共用回填管線。
- 正常畫面不新增技術值；失敗提示維持簡潔。
- 執行完整既有測試、Python 編譯檢查及差異檢查。

## 安全與上線閘門

- 所有自動化測試只使用 synthetic fake worksheet，不讀寫正式訂單或正式 Google Sheet。
- 在獨立 `codex/*` 分支完成實作與 fresh-context 程式審查。
- 本地驗收完成後，推送分支與部署正式 Streamlit 站前另向使用者取得同意。
- 部署後先做不觸發製單的唯讀 UI／快取檢查。
- 真正回填驗證只能使用使用者指定的安全測試單，不得自行拿正式訂單試寫。
- 常駐與商業個資合規託管遷移另立規格，不與本次短期修復混合。
- 使用者要求應用程式實作前切換至 GPT-5.6 Luna、推理強度 Max；若目前工作階段無法使用該模型，必須停在實作閘門。

## 完成條件

- 首次進站不需手動按鈕即可看到兩份可用資料，後續使用者可重用 20 分鐘共享快照。
- 活躍頁面可在安全狀態下維持資料新鮮，且不宣稱休眠期間仍會刷新。
- 郵局製單只剩「待製郵便運單」一個入口，原新版 UI 體驗沒有非必要退步。
- 工作表列數不足時能先擴列；每個包裹的 B、C、D、J 均有讀回驗證。
- 追加製單只依本次明確結果新增多筆；重試不重複寫入，異常結果不被默認合法。
- 回填失敗不再靜默顯示完成，且日誌不洩漏個資。
- 全套測試、編譯檢查、差異檢查與獨立審查通過後才可申請部署。
